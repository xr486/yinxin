# BOM 子件版本按父 BOM 行固定（修复「切换版本级联影响其他 BOM」）

> ⛔ **状态：已回滚、方案未落地（2026-08-17）**。本设计仅为方案文档，`bom_lines_all.component_version`
> 字段虽曾建但未有任何代码使用，已于 2026-08-17 `DROP COLUMN` 删除（全库 35 行钉定值均为 NULL）。
> 如后续要真正解决「切换版本级联污染」，需重新评估并实现下述 `getActiveLines`/`buildMindmapTree` 逻辑，
> 再重建该字段——不要假定字段仍存在。

## 问题
原「连接跟随」模式下，父 BOM 行只存 `component_item + qty`，显示子件版本时统一调用
`latestHeader()`（即子件的 `is_current` 当前生效版本）。因此当用户通过「设为当前生效」改了
某个子件物料的当前版本后，**所有**引用该子件的父 BOM 都会跟着变版本，造成级联污染。

典型场景（库内真实数据，物料 `78000022`）：
- `78000022` 有 v1(已审核)、v2(未审核)，当前生效 = v2。
- 被 `78000020`、`29937355` 两个父 BOM 同时引用。
- 旧逻辑：两个父 BOM 显示的 `78000022` 永远都是同一个当前版本，无法让 A 父显示 v1、B 父显示 v2。

## 方案
在 `bom_lines_all` 增加可空字段 `component_version`，用于**按父 BOM 行**固定该子件显示哪个版本：
- 字段为空（历史数据默认）→ 仍跟随子件 `is_current` 当前生效版本（向后兼容，旧行为不变）。
- 字段有值 → 该父 BOM 行渲染子件时强制使用指定版本。

此字段**只作用于当前这一行父 BOM**，不影响其他引用同一子件的 BOM，从而消除级联。

## 数据库改动（正向 / 回滚）
- 正向：`开发文档/SQL_2026-08-17_bom_line_version_pin.sql`
  ```sql
  ALTER TABLE bom_lines_all
    ADD COLUMN component_version VARCHAR(20) NULL
    COMMENT 'pinned child version for this parent line; NULL=follow child current(is_current)';
  ```
- 回滚：`ALTER TABLE bom_lines_all DROP COLUMN component_version;`

未新增表、未改动 `sf_item_no`。

## 代码改动（BOMSetup.php）
1. `getActiveLines()`：SELECT 增加 `component_version`。
2. `renderHierarchy()`：
   - 行版本解析：`$lineVersion = $ln['component_version']`；非空则 `headerByVersion(子件, $lineVersion)`，否则 `latestHeader(子件)`；pin 失效兜底回退 `latestHeader`。
   - 递归展开子件时传入 `$lineVersion`（替代原来的顶层 `$version`），使更深层级也沿用本行 pin。
   - 层级表新增「子件版本」列：有 BOM 的子件显示版本 `<select>`（选项=跟随当前 / 各版本），切换仅改本行。
3. `buildMindmapTree($version)`：支持按行 `component_version` 向下传递版本上下文（思维导图与层级表一致）。
4. 新增 AJAX `op=set_line_version`：按 `bom_header_id + component_sequence_id` 更新该行
   `component_version`；**已审核父 BOM 全功能冻结（Option A）拦截**，并校验版本确实属于该子件。
5. 前端 `.child-ver-sel` change：提交 `set_line_version`，成功后整页刷新以应用新「连接跟随」上下文。

## 行为约定
- 「设为当前生效」按钮：仍用于设置子件物料的**默认**当前生效版本（影响 `component_version` 为空的行）。
- 层级表「子件版本」下拉：设置**仅当前父 BOM 行**的显示版本，互不影响。
- 已审核 BOM 下禁止修改子件版本（与既有冻结规则一致）。

## 验证
- 数据级（已通过）：库内对 `29937355` 的 `78000022` 行 pin v1 后，
  `29937355` 显示 v1、`78000020` 仍显示其当前 v2；还原后数据干净。
- 浏览器验证（建议）：登录后打开 `BOMSetup.php?view=29937355`，在 `78000022` 行将「子件版本」
  改为 v1，刷新后该 BOM 显示 v1；再打开 `BOMSetup.php?view=78000020`，确认 `78000022` 仍为 v2（未受影响）。
